## Why Twitter now, and the ONE naming rule that governs this whole document

The owner's stated priority was **TikTok and Instagram first, then everything else**. Both ship. Twitter is next. This ordering is not re-argued here.

### Prose says "Twitter". Code says `'x'`. This split is deliberate and load-bearing — do NOT "fix" either side.

The owner asked, directly, that the platform be called **Twitter** — never "X" — in all prose. So every sentence in this plan, every changelog line, every commit **subject/body**, and every user-facing string says **Twitter**.

But the internal platform **CODE stays `'x'`**, because those are *identifiers*, not names, and renaming them would churn a large surface for nothing:

| Stays `'x'` (identifier — DO NOT rename) | Says "Twitter" (prose/user-facing) |
|---|---|
| `PostRef` arm `{ p: 'x'; id }` | This plan's prose and title |
| `ref.p === 'x'`, `case 'x':` | Commit messages |
| `refKey` → `x:{id}`; `parseRefKey` `case 'x'` | `docs/CHANGELOG.md` |
| Route/canonical URLs on **`x.com`** | `APPLICATION.x = 'Twitter'` (already set — the user-facing "posted via" line) |
| `THEME.x`, `APPLICATION.x` **keys** | The error-embed text |
| `ESCAPE` token `/x/…`, `HOST.x = 'x.com'` | Function/dir names use "Twitter" (see below) |

**Directory and function names use "Twitter", matching the existing convention.** The platform directories are named by full name (`src/platforms/bluesky/`, `…/tiktok/`, `…/instagram/`), and the functions by full name (`fetchBluesky`, `normalizeTikTok`, `fetchInstagram`). Twitter follows suit: **`src/platforms/twitter/`**, `fetchTwitter`, `normalizeTwitter`. This is not a contradiction of "code says `'x'`": the short code `'x'` is the **`Platform`-enum value**, and the enum value is what stays `'x'` everywhere it appears. The directory/function name is the full-name convention every other platform already uses.

`src/render/mastodon.ts` already states this exact rule in its `APPLICATION` docstring — read it. `APPLICATION.x` was caught mid-review shipping the literal `'X'` and corrected to `'Twitter'` before any client saw it (2026-07-20). An implementer who "consistency-fixes" `{p:'x'}` to `{p:'twitter'}`, or who renames `x.com` URLs, has misread this section and broken cache keys, refKeys, and every `/_media/` URL. An implementer who ships the word "X" to a user has misread it the other way.

## Global Constraints

(Inherited from Phases 1–3a and Instagram — every task's requirements implicitly include all of these.)

- Zero runtime dependencies. devDependencies exactly: `@cloudflare/workers-types`, `typescript`, `wrangler`.
- **Assert on CONTENT, never on status code — and never on `content-type` either.** Twitter makes both lie, and it makes them lie in *three* distinct ways on the syndication endpoint alone (the exact hazard Task 3 pins):
  - **200 + `{}`** when the derived token is missing/wrong.
  - **200 + `TweetTombstone`** when the post is age-gated (the credential wall).
  - **404 + an HTML "poodle" page** when the id names no post — a 404 status from a JSON endpoint, serving HTML.

  Status and content-type discriminate none of these. Assert on the presence of real post fields (`__typename === 'Tweet'`, non-empty text/author).
- Never guess an ambiguous path. Ambiguity resolves to `{kind:'ambiguous'}`, never a platform. `/{username}` stays `['x','ig']`.
- **Never dead-end a root token.** Shape-match with fallthrough. (`/x/status/123` under `@x` was the original defect class.)
- Never proxy media bytes. `/_media/*` reads the Post cache and 302s. Twitter media makes this trivially safe — see fact 5.
- Renderers emit `/_media/{refKey}/{index}` URLs, never raw CDN URLs — including in `media_attachments` and in the poster `preview_url`. **NEVER point `preview_url` at the mp4** (the 2026-07-19 defect).
- Never `Vary: User-Agent`. Client class goes in the cache key.
- Cache keys derive from `refKey(ref)`, never the raw path. `x:{id}` is the key; every URL spelling of one tweet collapses onto it.
- Origin always derived from the request, never hardcoded.
- Log nothing identifying. No URLs, no tweet IDs, no handles, no IPs, no tokens. Counters only (`count()`), and **never log the guest token or the derived syndication token** — they are the two new secrets this phase touches.
- **Pure core:** fetchers do I/O; normalizers and renderers are pure and test with **no network**.
- **Do not touch `megapenispoopenfarten.sex`.** Staging only, for the entire phase.
- TDD: write the failing test, **RUN it**, confirm it fails for the right reason, then implement.
- Commit identity is pinned to `shamu4life`. Never pass `-c`, `--author`, or set `user.email`.

## THE EDGE-CACHE HAZARD — read before you run a single live test

This is a hard requirement on every verification step in this plan, not a footnote. It cost a full day on TikTok and was re-measured during Instagram.

Our embed HTML is edge-cached at Cloudflare **by PATH** (`respCacheKey(ref, client)` collapses every spelling and query strings are ignored). `src/render/fail.ts` sets `public, max-age=0, must-revalidate` on every HTML response, which fixes the origin side; a zone Browser-Cache-TTL rewrite still rewrites it on the way out, so a hit can *show* `max-age=14400` cosmetically. The real edge lifetime is bounded by `RESP_TTL = 900 s` (`src/cache.ts`) — **15 minutes, not four hours** (measured across the boundary during Instagram; see that plan's CORRECTION box).

Therefore, on every live test in Tasks 8–9:

> **EVERY LIVE TEST MUST USE A TWEET URL THAT HAS NEVER BEEN FETCHED BEFORE** (a different id — not a new query string, not a new UA), **or wait 15 minutes.**

Corollary: **any conclusion drawn from a same-URL retest inside the 15-minute window is void.** Failure renders are **not** cached at all (`worker.ts` returns the error embed with no `cache.put`), so a nonexistent id is free — use one for cache-key or routing experiments. Budget tweet IDs accordingly: collect **at least ten** fresh tweets before Task 8 (two text, two single-photo, two multi-photo, two video, one gif, one age-gated), so the staging pass (Task 8) and the human gate (Task 9) each get URLs the other never touched.

## NO WORKERS-EGRESS PROBE THIS PHASE — and why that is a decision, not an omission

Instagram and TikTok each opened with a blocking Workers-egress probe because every fact they rested on came from a residential IP and the platform was known to treat Cloudflare differently (IG's 599 KB decoy; TikTok's aweme 404). **Twitter has no such gap.** The recon measured **both** fetch paths — syndication (Path A) *and* guest GraphQL (Path B) — from real Cloudflare Workers egress and got results **byte-identical** to residential:

- Syndication `tweet-result` with the derived token: full text, author, photos, and unsigned mp4 variants, from Workers egress, on text/photo/video posts. 15/15 rapid calls succeeded.
- Guest-token activation + `TweetResultByRestId`: `__typename: "Tweet"`, full text, video variants, `x-rate-limit-remaining: 499` per token — from Workers egress.
- Age-gated posts return `TweetTombstone` from **both** paths and **both** egresses — the wall is credential-based, not IP-based.
- Media (`pbs.twimg.com`, `video.twimg.com`) is **0 redirect hops, unsigned, not IP-bound, cookie-free** from both egresses, including a July-2026 video.

**Do NOT add a throwaway `src/probe.ts` + `/_probe/` endpoint this phase.** There is nothing for it to settle that the recon has not already settled from the same network our Worker runs on. Cargo-culting the IG/TikTok probe task here would be building a debug egress endpoint to re-measure a resolved question — pure risk (a caller-supplied-id fetch on a public origin) for zero information. If, mid-implementation, you believe a *specific* live Workers check is genuinely unresolved (e.g., the guest GraphQL `qid`/`features` set drifted and Path B 400s), **justify that specific gap and probe only it from the existing staging worker in Task 8's verification** — do not stand up a general probe module. The recon is the citation; cite it in the fetcher headers.

The **one** thing the recon could not measure is what only a real Discord client can: does Discord's *media proxy* (its IPs, not ours) play the video, and does the accent colour look right. Those are Task 9, exactly as for every prior platform.

## Twitter verified facts

Measured live from BOTH residential AND Cloudflare Workers egress, 2026-07-19 (full text `/tmp/twitter-recon.txt`; FxEmbed read at HEAD `9f57d264`, dated 2026-07-18). Cite these; do not re-derive them and do not contradict them. Where something is *not* verified it says so.

### 1. PATH A — syndication is PRIMARY. One GET, no credentials.

```
https://cdn.syndication.twimg.com/tweet-result?id={ID}&lang=en&token={TOKEN}
```

`token` is **derived client-side, not issued**:

```js
token = ((Number(id) / 1e15) * Math.PI).toString(36).replace(/(0+|\.)/g, '')
```

- **The float imprecision is INTENDED.** `Number(id)` loses precision on a 19-digit id, but Twitter's own web client computes the token with the identical IEEE-754 JS math, so our token matches theirs exactly. **Do NOT "fix" this to BigInt** — a "more correct" token is the *wrong* token. Verified: `id=20 → token=6dq1a2xwd93` returns jack's "just setting up my twttr".
- **CONTENT-ASSERT TRAP:** without the token you get **HTTP 200 with body `{}`**. Status and content-type are useless. Assert on `__typename === 'Tweet'` and real fields.
- Returns full text, author, and media: photos as `pbs.twimg.com/media` URLs, video as **unsigned** mp4 variants (multiple resolutions) plus an HLS `m3u8` we ignore.
- No `x-rate-limit-*` headers; `cache-control: max-age=60`, Fastly-fronted, cheap. This is the primary path **because** it is the cheapest and needs no token dance, no bearer, no cookie.

### 2. PATH B — guest GraphQL is the FALLBACK.

```
POST https://api.x.com/1.1/guest/activate.json   -> {"guest_token": "..."}
GET  https://api.x.com/graphql/{qid}/TweetResultByRestId?variables=...&features=...&fieldToggles=...
```

with the **public web bearer** (hardcoded, FxEmbed `src/constants.ts:60` — `AAAAAAAAAAAAAAAAAAAAANRILgAAAAAAnNwIzUejRCOuH5E6I8xnZz4puTs%3D1Zv7ttfk8LF81IUq16cHjhLTvJu4FA33AGWWjCpTnA`; it is a public constant, not a secret), plus `x-guest-token`, a random `x-csrf-token`, `x-twitter-active-user: yes`, and `Cookie: guest_id=v1%3A{gt}; ct0={csrf}` (FxEmbed `packages/atmosphere/src/providers/twitter/fetch.ts` ~126-135).

- The guest token is **free and reusable** (~500-request budget, `x-rate-limit-remaining: 499`). Reuse it through the **runtime fetch cache**, the FxEmbed form: put `cf: { cacheEverything: true, cacheTtl }` on the `activate.json` fetch **Request**, so workerd serves the cached activation until the TTL lapses; spec §Credentials sets that TTL to 2 hours. Do **NOT** also hand-manage `caches.default` for the token — `caches.default` is the Cache API (`match`/`put` on Request/Response objects), a *different* mechanism, and you cannot "store with `cf`" into it; pick one, and this phase picks the `cf` fetch-cache form (Task 4 pins this). No KV binding. And **assert the activation on the presence of the `guest_token` string field, never on `res.ok`** — a 200 carrying no token is still a failure (the phase's assert-on-content rule).
- **`qid` is `TweetResultByRestId`'s query id** (recon observed `f2sagi1jweVHFkTUIHzmMQ`). qids and the `features`/`fieldToggles` sets **DRIFT** — Twitter rotates them. Keep them current from FxEmbed's source, and treat a Path-B `400`/`404` in Task 8 as "the qid/features drifted", not "the design is wrong". This is the single most fragile thing in the phase, which is exactly why it is the **fallback**, not the primary.
- **GOTCHA 1 — `TweetWithVisibilityResults`.** Some posts return `result.__typename === "TweetWithVisibilityResults"`, where the payload is at `result.tweet.legacy`, **NOT** `result.legacy`. Naive `result.legacy` yields empty text. Unwrap both.
- **GOTCHA 2 — single-status only.** `TweetResultByRestId` is the **only** guest-viable query (FxEmbed's catalog marks every other — `TweetDetail`, `UserTweets`, `SearchTimeline`, … — `requiresAccount: true`). Threads, profiles, and search require an account. Single-status fetch is exactly this project's surface. Do not plan on anything else.

### 3. AGE-GATED posts are BLOCKED credential-free — build the SEAM, ship it EMPTY.

Confirmed by live measurement on both paths and both egresses: an age-gated post returns **`__typename: "TweetTombstone"`** with no text, no media, no author, no counts. The same IDs through *credentialed* FxEmbed return full content — so the post exists and the wall is credential-surmountable.

- **Detect the gate on `__typename === 'TweetTombstone'`**, on both paths. The recon corrects the spec here: the *current* shape is `TweetTombstone`, **not** `TweetUnavailable`/`NsfwLoggedOut`, and it carries **no `reason` field**. FxEmbed's escalation branch keys on `result.reason === 'NsfwLoggedOut'` (`fetch.ts:252`), which would **not** fire on this shape — so keying on `reason` would silently miss every gated post the recon measured. Key on the `__typename`.
- **200, again.** Gated posts are HTTP 200. Status tells you nothing.
- A tombstone is **NOT a `sensitive` post** (spec §`sensitive`): it carries no text to render, so it never becomes a `Post`. It is an `Outcome.failure`. Do not confuse it with `possibly_sensitive` (fact 8) — that is an ordinary, fetchable, sensitive post that we DO render, with the `[sensitive]` marker.
- **THE SEAM SHIPS EMPTY, AND STAYS EMPTY.** A named function returns `null` because there are no
  credentials, and an age-gated tweet becomes an honest `age_restricted` failure (see Task 5). This
  is a **tested boundary, not a TODO**: a test asserts the seam is reached on a tombstone and that,
  empty, it yields `age_restricted`.

  Other projects fill this seam with farmed logged-in accounts. This one does not, and the
  description of how they do it has been removed from this plan — it was written as recon and
  reads as intent. The shipped decision is the one above: we do not hold accounts, so a post
  behind a login wall is reported as behind a login wall.

### 4. Media types, and the animated-GIF trap.

Twitter media arrives as (syndication) `mediaDetails[]` and (guest) `legacy.extended_entities.media[]`, each entry carrying `type`, `media_url_https` (the still), and for motion a `video_info.variants[]` list:

- **`type: "photo"`** → `{ kind:'image', url: media_url_https, w, h }`.
- **`type: "video"`** → `{ kind:'video', url: <best mp4 variant>, poster: media_url_https, w, h, duration? }`.
- **`type: "animated_gif"`** → **`{ kind:'video', … }`, NOT `kind:'gif'`.** This is the trap and it gets its own fact: a Twitter "GIF" is delivered as an **mp4 with no audio**, not a `.gif` file. Our `Media.kind` `'gif'` means *"the url IS an animated .gif file"* and maps to Mastodon attachment `image` (`render/mastodon.ts` `ATTACHMENT_TYPE`). Mapping Twitter's animated_gif to `kind:'gif'` would put an **mp4 URL into an image attachment** — the exact 2026-07-19 poster defect (Discord requests a still, receives mp4 bytes, drops the rich card). So map it to `kind:'video'` with a real poster; it renders a silent looping inline player, which plays. The `'gif'` kind stays unused, as `mastodon.ts` already notes.

**Best-mp4 selection — by `content_type` FIRST, then bitrate:** from `video_info.variants`, **filter to `content_type === 'video/mp4'` first**, then pick the **max `bitrate` among those**, defaulting to the sole mp4 when there is only one. Do **NOT** filter or gate on a *truthy* `bitrate`: a Twitter `animated_gif` mp4 frequently carries `bitrate: 0` or omits it entirely, and a truthy-bitrate filter would discard the only playable url, leaving a dead player. Ignore `application/x-mpegURL` (the HLS `m3u8` — Discord cannot play it). This selection is **shared** by both source shapes, because `video_info.variants` is the same structure in syndication and in guest.

**`preview_url` / poster is MANDATORY on a video attachment** and must be the still image (`media_url_https`), never the mp4. `Media.poster`, `MediaIndex`'s `{poster:N}`, router's `poster{N}` segment, `pickMedia`'s poster branch, and `posterUrl()` in `mastodon.ts` are ALL already built and tested (Instagram/TikTok). Twitter's only job is to populate `Media.poster` on every video/gif entry.

### 5. Media is the best of any platform here — 0 hops, unsigned, no POST_TTL constraint.

Measured cookie-free, `redirect: 'manual'`, magic-byte-asserted, from both egresses:

| Asset | Hops | Bytes | Magic | Verdict |
|---|---|---|---|---|
| video mp4 720p (2022) | **0** | 17,929,563 | `ftypisom` | real MP4 |
| photo `?name=orig` | **0** | 1,131,387 | `ffd8ff…JFIF` | real JPEG |
| video mp4 720p (**Jul 2026**) | **0** | 15,537,449 | `ftypisom` | real MP4 |

- **Zero redirects.** Our `/_media/` 302 → CDN is therefore the ONLY hop Discord's proxy sees — comfortably inside the one-hop budget whose violation broke TikTok video. **There is no `withResolvedVideo` analogue and there must not be one** (see Task 5): TikTok needed one because its playable URL is itself a 302; Twitter's is not.
- **No signing, no expiry, no IP binding.** The only query param is `?tag=14`, and the recent video fetched **identically with `tag` stripped entirely**. So Twitter puts **NO constraint on `POST_TTL`** — do not lower it, and do not add an `oe=` expiry check (that was Instagram's concern; Twitter has no signature). The `media_url_https` still and the mp4 flow through the *same* attachment + poster path Instagram/TikTok already use.

### 6. Crawler-UA fallback exists but is text-only — do NOT build on it.

`x.com/{user}/status/{id}` with a `Discordbot`/`Telegrambot` UA returns `og:description` with full text, but `og:image` is an unusable indirection stub (`jf.x.com/images/media-preview/{id}`) and the HTML contains no `pbs.twimg.com/media` and no `video.twimg` reference at all. Both API paths dominate it. Mention it exists as a last-ditch text-only degrade; **build nothing on it this phase.**

### 7. WHAT ALREADY EXISTS — Twitter is CHEAPER than TikTok or Instagram was. Verify, don't rebuild.

Recon-confirmed present in the tree today, needing **no change**:

- `src/router.ts` — `x()` already matches `/{handle}/status/{id}`, `/i/status/{id}`, `/i/web/status/{id}`, and collapses trailing `/photo/N` and `/video/N` onto the same `{p:'x', id}`. `matchPost` dispatches `'x'` forced (`/x/…`) and unforced. The `/x/…` escape hatch + fallthrough are built and tested (`/x/status/123`, `/x/x/status/123`, `@api`, `@users`, `@_oembed` all covered). **The routing task is mostly VERIFICATION.**
- `src/types.ts` — `PostRef` already declares `{ p:'x'; id:string }`. **No type change this phase.**
- `src/refkey.ts` — `refKey` mints `x:{id}` and `parseRefKey` inverts it. Round-trips already.
- `src/render/embed.ts` — `THEME.x = '#000000'` exists (a sane Twitter black; **its value is a human-gate item**, fact 9).
- `src/render/mastodon.ts` — `APPLICATION.x = 'Twitter'` exists and is correct (fixed 2026-07-20, never shipped as 'X').
- `src/render/chooser.ts` — `HOST.x = 'x.com'`.
- `src/analytics.ts` — `Outcome2` already declares **`'age_restricted'`**. The age-gate counter is already a first-class outcome. **No analytics change.**
- Everything platform-agnostic: `cache`, `statusid`, `media`, `classify`, the chooser, text/embed/telegram/discord renderers, the poster route, the video head, the gallery — all already exercised by three platforms.

**The real work is:** the two fetchers (syndication + guest), the two-shape normalizer (populating `quote`/`replyTo` from both shapes — the renderer already consumes them), the worker dispatch arm, the empty credential seam, and one small shared display-name map so the *failure* embed reads "Twitter", not the code `'x'`.

### 8. `possibly_sensitive` IS a real signal here — unlike TikTok/IG/Threads.

Spec §`sensitive`: Twitter exposes `possibly_sensitive` on a **successfully fetched** post. So `sensitive: !!possibly_sensitive` (default `false`), NOT the always-`false` that TikTok and Instagram use. A `possibly_sensitive: true` post that is *not* age-gated fetches normally (syndication/guest return it) and renders with the existing `[sensitive]` marker (`isSensitive`/`contentWithMarker` already handle it — no new render code). **This is a different thing from the age-gate** (fact 3): sensitive-but-fetchable vs. gated-and-walled. Keep them apart in the normalizer and the dispatch.

### 9. THE TWO HUMAN-GATE VALUES — `THEME.x` and playback.

- `THEME.x = '#000000'` is a placeholder no real client has rendered for Twitter. It is one line in `embed.ts` if the human says it looks wrong. **Human-gate item, not a blocker.**
- Whether Discord's media proxy plays a `video.twimg.com` mp4 from our single-hop 302 is unmeasurable locally (Discord fetches from Discord's IPs). Fact 5 makes it *likely* (0 hops, unsigned, cookie-free — strictly better than TikTok, which plays today), but only Task 9 settles it.

`src/platforms/twitter/normalize.ts`. Load-bearing decisions, each with a test above:

- **`syndicationHasTweet(json)` is the ONE content assertion**, exported, reused by the fetcher (Task 3) so there is one spelling — the rule TikTok's `videoDetailScope` and Instagram's `shortcodeMedia` both state. It returns `true` only when `json` is an object with `__typename === 'Tweet'` and a string `text` and a `user`. A `TweetTombstone`, a `{}`, or anything else is `false`.
- **Naming split, restated in the file header:** this file lives at `src/platforms/twitter/` and its functions say "Twitter", but every `ref.p` value, `refKey`, and URL is `'x'` / `x.com`. Put the split in a header comment (mirror `mastodon.ts`'s `APPLICATION` docstring) so nobody "consistency-fixes" it.
- **Author + canonical:** handle from `user.screen_name`, name from `user.name || screen_name`, avatar from `user.profile_image_url_https` (https-guarded). `canonical = new URL(`https://x.com/${screen_name}/status/${ref.id}`).href` — through `new URL().href` so a hostile field cannot inject CR/LF into the `location` header `worker.ts` builds from it (the 500 fixed in `4655ee8`; TikTok's normalizer documents the same). When `screen_name` is untrustworthy, fall back to `/i/status/${ref.id}`, which resolves without a handle.
- **`created_at`:** syndication is ISO (`"2006-03-21T20:50:14.000Z"`) — `new Date(str)` parses it directly. **Validate the Date object** (`Number.isNaN(d.getTime())` → null), not the string; an escaped Invalid Date is an uncaught `RangeError` 500 in `mastodon.ts`'s bare `toISOString()`. Mirror TikTok's/Bluesky's date-validation scar.
- **Media** via the shared `mediaFrom(list)`:
  - `photo` → `{kind:'image', url: httpsUrl(media_url_https), w, h}`.
  - `video` → `{kind:'video', url: pickMp4(video_info.variants), poster: httpsUrl(media_url_https), w, h, duration?}`.
  - `animated_gif` → **`{kind:'video', …}`** with poster (fact 4 — never `kind:'gif'`).
  - `pickMp4(variants)`: **filter to `content_type === 'video/mp4'` first**, then choose the max `bitrate` **among those**, defaulting to the sole mp4 when there is one; ignore `application/x-mpegURL`. Do **NOT** gate on a truthy `bitrate` — an `animated_gif`'s only mp4 variant often has `bitrate: 0`/none, and dropping it leaves a dead player (see the `bitrate:0` test above). If there is no mp4 at all, the entry **degrades to its still as `kind:'image'`** — never a dead player (Phase 1's I-1 lesson).
  - Non-https entries **skipped**, not emitted. Dimensions via a `dim()` (0-for-unknown) helper, copied from TikTok — do not re-derive.
- **Counts:** route every candidate (`favorite_count`, `reply_count`/`conversation_count`, `retweet_count` — whichever the fixture carries) through a `count()` helper that rejects NaN/negative/non-integer and **omits** the key. Copy TikTok's `num()`/`count()` pair verbatim; it carries three scars.

The three syndication trap-states (fact 1, §Global Constraints) call for **three** different responses, and one `Post | null` cannot express them:

| What happened | Result | Downstream |
|---|---|---|

| `__typename === 'TweetTombstone'` | `{ ok: false, reason: 'age_restricted' }` | seam → `age_restricted` counter |

Collapsing them would either pointlessly hammer guest on every gated post or silently miss the token-algo-broke case.

#### The orchestration, and why the fallback triggers are what they are

```
fetchTwitter(ref, env):
  a = await fetchSyndication(ref)                 # Path A, primary
  if a.ok:                     return { ok, source: 'syndication', data: a.data }
  if a.reason === 'age_restricted':               # the wall — guest walls too, so go straight to the seam
      cred = await fetchWithCredentials(ref, env)
      return cred ?? { ok: false, reason: 'age_restricted' }
  # a.reason === 'assert_fail' — token algo/endpoint may have broken; try the fallback
  b = await fetchGuest(ref, env)                   # Path B, fallback
  if b.ok:                     return { ok, source: 'guest', data: b.data }
  if b.reason === 'age_restricted':
      cred = await fetchWithCredentials(ref, env)
      return cred ?? { ok: false, reason: 'age_restricted' }
  return { ok: false, reason: 'assert_fail' }
```

- **`age_restricted` from syndication goes straight to the seam, skipping guest** — both paths wall age-gated content credential-free (recon), so paying for a guest fetch there is a wasted request that will only wall again. The seam is the only thing that can surmount it.
- **`assert_fail` from syndication tries guest** — that is the "maybe Path A broke" case the fallback exists for.
- **`fetchWithCredentials` returns `{source:'guest', data}`** so a *filled* seam feeds the same `fromGuest` normalizer (credentialed responses are guest-GraphQL-shaped). Empty, it returns `null` and the tweet is `age_restricted`.

## Notes for whoever picks this up next

**On the naming split.** `{p:'x'}` with `APPLICATION.x = 'Twitter'` is the clearest illustration in the tree that *code identifiers* and *user-facing prose* are different things with different owners. If a future platform tempts you to "unify" them, that temptation is the bug — the split is the design. `mastodon.ts`'s `APPLICATION` docstring is the canonical statement of it.

**On the two paths.** Syndication is primary because it is the cheapest to operate, not because it is the more robust to depend on — a rotating `qid` makes guest fragile to run, but both are fragile to *Twitter's whims*. There are **three independent** such whims, and the research doc (Task 8) lists them as a triage checklist: (1) the syndication token algorithm, (2) the guest `qid` + `features`/`fieldToggles` set, and (3) the hardcoded public web bearer — any one can rotate alone. Keep both paths. If Twitter breaks the syndication token algorithm, syndication `assert_fail`s and the fallback keeps the service alive; if Twitter breaks the guest `qid` or the bearer, syndication carries it. The day both paths break at once, the crawler-UA text-only fallback (fact 6) is the degraded floor — build it then, not now.

**On the empty seam.** It is a real, tested function returning `null`, not a comment. That is the difference between "a place credentials could go" and "a place credentials went untested until the day someone needed them". When it is filled, it returns `{ source:'guest', data }` and `fromGuest` already knows how to normalize it — the boundary was designed so the fill is additive.

**On what this phase deliberately did not build.** No probe module (egress is already verified — cite the recon), no `PostRef` change, no `analytics` change, no router change, no second poster mechanism, no `withResolvedVideo`, no `POST_TTL` change, no bespoke age-gate wording. Every one was considered and has a named reason for its absence. If you find yourself adding any of them, re-read the fact or task that rules it out first.
